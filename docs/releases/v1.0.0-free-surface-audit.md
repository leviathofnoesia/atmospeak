# v1.0.0 free-surface audit

Audited 2026-07-29. The licence branch `claude/wispr-alternative-revenue-rbjd04`
(= `main` + three licence commits) was audited first; on the strength of
Finding 1 below, **v1.0.0 ships from `main` instead**, which contains no licence
code whatsoever. Both bases are recorded here.

Scope: confirm the 0.5.3 free feature floor is intact and nothing free is gated,
half-shipped, or documented ahead of code.

## Verdict

**No free-path regressions on either base.** The free surface promised in
`README.md` and the 0.5.2–0.5.3 changelog entries is fully present in code.

On the shipping base (`main`) there is no licence check anywhere — not disabled,
absent — so the entitlement analysis below is a record of why the licence branch
was excluded from v1 rather than a description of what ships.

## Entitlement gating

The licence work is purely additive. Verified by grepping every reference to
`license` / `entitlement` / `Feature::` outside the licence module:

- The only consumers of licence state are `LicensePanel.tsx` and three commands
  (`activate_license`, `deactivate_license`, `get_license_status`).
- No call site in `dictation_engine`, `polish`, `cleanup`, `injection`,
  `recorder`, `runtime`, `shortcuts`, `model_downloader`, or `db` reads
  entitlements. The dictation path never consults the module.
- Every `Feature` variant describes capability that does not exist yet:
  `CompliancePack`, `VoiceMacros`, `McpServer`, `IdeAwareness`, `Sync`,
  `TeamSharedVocabulary`. None maps to a shipped feature.
- Every licence failure path resolves to `Entitlements::free()` — absent key,
  unreadable keyring, forged signature, out-of-window build. `license::load()`
  cannot fail into an error, so an absent or invalid licence cannot break
  dictation.
- Activation performs no network request; `src-license` has no HTTP dependency.

### Auto-polish fallback (acceptance cases 049–058, 064)

Confirmed by construction, not just by test: `polish_if_enabled` calls
`polish_text_inner` with `allow_setup: false`, so when the bundled runtime is
absent `resolve_endpoint_and_model` hits the `runtime_ready` check and bails
immediately with "download it from Settings → AI edit". The engine catches it,
emits a `polish-fallback` runtime event, and pastes the cleaned text. The auto
path is additionally capped at `AUTO_POLISH_TIMEOUT` = 750 ms. A missing runtime
therefore cannot produce a multi-minute hang — the download path is reachable
only from the explicit Settings/History action (`allow_setup: true`).

## Finding 1 — the Licence tab is dead UI in any shipped build

`TRUSTED_PUBLIC_KEYS` in `src-license/src/lib.rs:47` is the all-zero
placeholder, which by design rejects every key (`the_shipped_placeholder_key_trusts_nothing`).
That is the correct default — a build without a real public key must trust
nothing — but it means that in a shipped v1.0.0 the Licence tab presents a
"Licence key / Activate" form in which **every key fails**, for features that do
not exist and cannot be purchased.

This is the only half-shipped surface found. It does not gate or break anything
free; it is an honesty/polish issue on a release billed as a finished free
product.

**Resolution:** v1.0.0 ships from `main`, excluding the licence work entirely.
PR #12 remains open and should land alongside a real signing key and at least
one purchasable feature. Nothing in that PR is wrong — it is simply premature
for a release whose whole claim is that the product is finished and free.

### Native push-to-talk harness — unresolved on `main`

**Status: open. Not explained.** This section previously asserted an
environmental cause; that assertion was wrong and has been removed.

The harness spawns its own paste target: `scripts/native-injection-target.ps1`,
a WinForms `TextBox` hosted in a PowerShell process and titled "Native Injection
Target", which writes its contents to a temp file on every `TextChanged`. The
harness then polls that file for up to 5 s and requires it to equal the cleaned
transcript exactly.

Across four attempts on `main` the file stayed empty. The reported
`targetProcessName` was `Powershell` on two runs — which is the harness's **own**
target process, i.e. the correct window — and `Explorer` / `SearchHost` on the
other two. `injected: true` and `restoredTarget: true` were reported throughout.

So there are two distinct symptoms, and only the second is plausibly ambient:

1. **Correct target, no text.** Focus was restored to the right window but the
   `TextBox` never raised `TextChanged`, so `Ctrl+V` did not reach the focused
   control. Not explained. This is the one that matters, because it is the same
   restore-focus-and-paste path the product uses.
2. **Wrong target entirely** (`Explorer`, `SearchHost`). Consistent with another
   window taking foreground during the run.

What is known to work on this base: the paste-latency harness — same clipboard
write, `Ctrl+V`, focus restore, and clipboard restore path — passes on `main`
(86 ms / 300 ms budget, `restoredClipboard` and `restoredTarget` true, target
text matching). And the PTT harness itself passed earlier in the session on the
licence branch, whose dictation and injection code is identical to `main`
(`totalMs` 1650 / 2000, inject 81 ms, `processedDuringRecordingMs` 2040).

The failure also reproduces on a fully idle machine with no build running, so
"the desktop was busy" is not the explanation.

**It is not a v1.0.0 regression.** The failures were observed on unmodified
`main` before the release commit, and that commit changes no application source
at all — only version strings, manifests, README, CHANGELOG, and docs. Whatever
this is, it predates 1.0.0 and is present in the 0.5.3 code line.

**Most likely locus — unconfirmed.** The two harnesses differ in exactly one
meaningful way. `native-paste-latency-harness.mjs` calls `inject_text` with an
explicit `targetHwnd` and passes. `native-push-to-talk-harness.mjs` drives a
real dictation cycle and depends on the app capturing the target's window handle
from the foreground at listen-start. That points at focus capture during the
harness's dictation cycle rather than at the paste path, which is independently
proven working on this machine.

Note also that `targetProcessName: "Powershell"` does not discriminate: both the
WinForms paste target and the smoke script's own console are PowerShell
processes. Do not read that field as evidence either way — an earlier draft of
this audit did, and was wrong.

Treat this gate as **not passed on `main`** until someone reproduces it and
either gets a clean run or identifies the real cause. It should not be recorded
as green on the strength of the reasoning above.

Two further failures appeared in the earlier run set and cleared on retry:

1. `Native injection target HWND was invalid` — the target window did not report
   its handle before the harness polled.
2. A cold-ASR latency miss: `totalMs` 4076 with `processedDuringRecordingMs: 0`
   and `asrBackend: "host"`, i.e. the streaming path did no work during
   recording and everything landed in finalize.

Case 2 is worth a note for future release runs: the 2000 ms budget is documented
as a **warm** short-clip SLO, and the first run after a cold start can exceed it
legitimately. Treat a single cold miss as inconclusive and re-run warm rather
than as a regression signal.
